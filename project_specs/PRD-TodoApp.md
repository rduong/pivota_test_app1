# Product Requirements Document (PRD)
## Todo List App with User Management (TodoApp)

**Version:** 1.0  
**Date:** 2026-04-15  
**Status:** Validated  

---

## 1. Executive Summary

TodoApp is a single-page web application built with pure HTML, CSS, and JavaScript that enables teams and individuals to manage tasks with role-based access control. It provides a lightweight, portable todo experience gated by an invite-code registration system, allowing an administrator to control user access while users manage their own task lists — all without a backend or external database.

---

## 2. Problem Statement

### 2.1 Core Problem

Small teams and individual users need a simple, self-contained task management tool that doesn't require account sign-ups through third-party services, complex infrastructure, or external databases. At the same time, they need basic access governance so that only approved participants can use the system.

### 2.2 Pain Points

- **No access control in simple apps:** Most lightweight todo tools are either fully public or rely on complex OAuth setups. There is no middle ground for invite-only team access.
- **Backend dependency bloat:** Even simple productivity apps typically require a server, database, and authentication service — overkill for a small team or personal project.
- **Admin visibility gap:** Team leads and administrators often have no way to view or oversee their team members' tasks in lightweight tools.
- **Onboarding friction:** Existing tools require email verification, OAuth flows, or external identity providers just to let a new user join a shared workspace.

### 2.3 Target Users

- **Admins:** Power users who manage team membership, generate invite codes, and need visibility into all users' task lists.
- **Regular Users:** Team members or individuals who register via invite code and manage only their own todo items.

---

## 3. Product Vision

### 3.1 Vision Statement

To be the simplest possible invite-gated task management tool — fully portable, zero-backend, and usable by anyone with a browser.

### 3.2 Strategic Goals

- Deliver a fully functional todo app with zero server-side dependencies
- Implement invite-code registration as the sole access control mechanism
- Provide admin visibility into all user data within the same client-side session
- Ensure all state persists reliably via localStorage across browser sessions
- Keep the entire application deliverable as a single HTML file or minimal file set
- Use clean, professional typography (Google Fonts: Outfit) for a polished appearance

## 5. Feature Requirements

### F0: Application Shell & Navigation
**Description:** The foundational single-page application shell that handles routing between views (login, registration, admin dashboard, user dashboard) using client-side state. All views are rendered within a single HTML document without page reloads.

**Capabilities:**
- Single HTML file structure with all views as toggled sections
- Client-side view router driven by app state
- Persistent session state stored in localStorage
- Google Fonts (Outfit) loaded from CDN for all typography
- Responsive layout for desktop and mobile viewports

**Priority:** P0 (Critical — MVP requirement)

---

### F1: User Authentication & Session Management
**Description:** Handles login and logout for both Admin and User roles. Sessions are maintained entirely in localStorage. On page load, the app checks for an existing session and routes the user to the appropriate dashboard. No passwords are sent to any server.

**Capabilities:**
- Login form with username and password fields
- Session stored in localStorage (username, role, session token)
- Auto-login on page load if valid session exists
- Logout clears session state and returns to login view
- Role-based routing: Admin → Admin Dashboard, User → User Dashboard

**Priority:** P0 (Critical — MVP requirement)

---

### F2: Invite Code Registration
**Description:** New users can only register by providing a valid invite code generated by an Admin. The registration flow validates the code against stored invite data in localStorage, creates the user account, and marks the invite code as used.

**Capabilities:**
- Registration form: username, password, invite code
- Invite code validation against localStorage invite store
- One-time-use invite codes (invalidated after successful registration)
- New user account persisted to localStorage user store
- Graceful error messaging for invalid or already-used invite codes
- Redirect to user dashboard after successful registration

**Priority:** P0 (Critical — MVP requirement)

---

### F3: Admin — Invite Code Management
**Description:** Admins can generate unique invite codes that are used to gate new user registration. Each code is a unique string that can be shared with prospective users. Admins can view all existing codes and their usage status.

**Capabilities:**
- Generate a new unique invite code with one click
- Display invite code in copyable text field or modal
- List all generated invite codes with status (Unused / Used)
- Display which user redeemed a code (if used)
- Codes stored in localStorage invite store

**Priority:** P0 (Critical — MVP requirement)

---

### F4: Admin — User Management
**Description:** Admins have a user management panel listing all registered users in the system. From this panel, an admin can view any user's profile and access their todo list.

**Capabilities:**
- Display list of all registered users (username, registration date, role)
- Click-through to view any user's todo list
- Distinguish admin accounts from regular user accounts
- Read-only view of other users' data (no edit/delete of other users' todos from admin panel)

**Priority:** P1 (High — needed for admin oversight)

---

### F5: User — Todo Management (CRUD)
**Description:** Authenticated users can create, view, update, and delete their own todo items. Each todo item has a title, optional description, completion status, and creation timestamp. Data is persisted in localStorage scoped to the user's account.

**Capabilities:**
- Add new todo item (title required, description optional)
- Mark todo as complete / incomplete (toggle)
- Edit todo title and description inline or via modal
- Delete todo item with confirmation
- Display todos in a list, sorted by creation date (newest first)
- Filter view: All / Active / Completed
- Item count display (e.g., "3 of 7 completed")
- Data scoped per user in localStorage

**Priority:** P0 (Critical — MVP requirement)

---

### F6: Admin — Todo Visibility (Read-Only)
**Description:** Admins can navigate to any user's todo list and view all of their items in a read-only mode. This gives admins full visibility into team progress without being able to modify other users' data.

**Capabilities:**
- Admin dashboard lists all users with link to view their todos
- Read-only todo list view showing all items for selected user
- Clear visual indicator that admin is viewing another user's data
- Back navigation to admin user list

**Priority:** P1 (High — core admin capability)

---

### F7: Data Persistence Layer
**Description:** All application data (users, sessions, invite codes, todos) is stored in and retrieved from the browser's localStorage. The data model uses namespaced keys to avoid collisions. No external API calls are made for data storage.

**Capabilities:**
- Namespaced localStorage keys (e.g., `todoapp_users`, `todoapp_todos_{username}`, `todoapp_invites`, `todoapp_session`)
- JSON serialization/deserialization for all data objects
- Data integrity: graceful handling of missing or malformed localStorage data
- Initialization: seed default admin account on first app load if no users exist

**Priority:** P0 (Critical — underpins all features)

---

### F8: Default Admin Bootstrapping
**Description:** On first load of the application (empty localStorage), a default admin account is automatically created. This allows the admin to immediately log in, generate invite codes, and start onboarding users without a separate setup step.

**Capabilities:**
- Detect first-run state (no users in localStorage)
- Auto-create default admin credentials (e.g., username: `admin`, password: `admin123`)
- Display first-run notice with default credentials on login screen
- Admin can (optionally) change password after login

**Priority:** P0 (Critical — ensures app is usable out-of-the-box)

## 7. Success Metrics

- **Core Functionality:** Admin can generate invite codes and users can register and manage todos within 5 minutes of first opening the app
- **Data Persistence:** 100% of user data survives a browser refresh and tab close/reopen
- **Role Enforcement:** Admin features are completely inaccessible to User-role accounts (verified via UI and direct localStorage inspection)
- **Invite Validity:** Each invite code can only be used once; second use displays an appropriate error
- **Portability:** Application runs correctly when opened as a local `file://` URL with no web server
- **Accessibility:** Zero critical WCAG 2.1 AA violations on primary flows (login, registration, todo management)
- **Code Size:** Total JavaScript under 500 lines; total CSS under 300 lines (indicative of simplicity target)

## 8. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| localStorage data loss on browser clear | Medium | High | Display prominent warning about data storage limitations; consider export feature in future |
| Client-side access control bypass | Medium | Medium | Acknowledge limitation in documentation; enforce consistent role checks on every state transition |
| Invite code brute-forcing | Low | Low | Use sufficiently random/long codes (UUID or similar); acceptable risk for a client-side-only app |
| localStorage storage quota exceeded | Low | Medium | Implement data size checks; display warning if approaching quota |
| Cross-browser localStorage inconsistencies | Low | Low | Test against target browsers; use standard Web Storage API only |
| First-time user confusion about default credentials | Medium | Low | Display clear first-run notice with credentials on login page |

## 10. Out of Scope

The following are explicitly excluded from this release:

- Real-time collaboration or multi-tab sync
- Native mobile application
- OAuth or third-party authentication (Google, GitHub, etc.)
- External database or backend server
- Email notifications or invite link delivery
- Admin ability to edit or delete other users' todos
- User ability to share todos with other users
- Password reset flow (no email backend available)
- Data export/import functionality
